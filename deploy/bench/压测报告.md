# 情侣小窝 · 服务端压测报告

> 用 wrk 对 Spring Boot 版服务端做只读接口压力测试，目标：量化 Cache-Aside 缓存收益、定位单机承载拐点，为容量评估提供可复核数据。

## 一、测试环境

| 项 | 值 |
|---|---|
| 服务器 | 阿里云 ECS，华北 2（北京），**2 vCPU / 2 GB** |
| 部署 | 单实例 Spring Boot 3 + JDK 17，内嵌 Tomcat，systemd 常驻 |
| 数据库 | MySQL 8（本机）、Redis 7（本机 db5） |
| 压测工具 | wrk，与被测服务**同机**跑 `127.0.0.1:8080`，排除公网带宽/延迟干扰 |
| 关键参数 | Tomcat `threads.max=100`、`accept-count=50`；HikariCP `maximum-pool-size=10`、`connection-timeout=3s` |
| 数据量 | 隔离 bench 家庭，含 **50 道菜 / 50 条备忘**，普通列表接口 |
| 鉴权 | mock 登录拿真实 JWT；每个请求经拦截器验签 + 查 Redis 黑名单 |
| 流量类型 | 仅只读 GET，不污染数据 |

## 二、固定并发对比（20 连接，压 20 秒）

| 接口 | 数据来源 | QPS | 平均延迟 | P99 |
|---|---|---:|---:|---:|
| `/ping` | 纯 Web 层，不查库/不验 token | **406** | 50.5ms | 136ms |
| `/dish/list` | **Redis 缓存命中**（Cache-Aside） | **112.9** | 176.8ms | 322ms |
| `/memo/list` | **MySQL 直查**（无缓存，列表 + 批量查创建人） | **86.9** | 228.7ms | 358ms |

**缓存收益：QPS 提升 1.30 倍；平均延迟下降 22.7%，P99 下降 10%。**

### 为什么只有 1.3 倍而不是 10 倍（关键归因）

缓存收益 = 数据读取省下的时间 ÷ 单个请求的总耗时。这两个接口的共同固定开销占了大头：

1. JWT 拦截器：每次都做一次 HMAC 验签 + 一次 **Redis 黑名单查询**（缓存命中接口也省不掉）；
2. 50 行数据的 JSON 序列化与返回（约 0.8 MB/s）；
3. Tomcat 线程调度 + wrk 与 Java 同机抢 2 个 CPU。

真正的差异只有数据来源：Redis 读 1 次 vs MySQL 查 `memo` + 批量查 `user` 两次 SQL。在 50 行、且走 `family_id` 索引的场景下，MySQL 这两次查询本身只要几毫秒，与 Redis 的 1ms 差距被固定开销稀释。

**结论：缓存倍数不是常数，取决于"数据读取在总耗时中的占比"。** 当数据量增大、查询变复杂（多表 JOIN/聚合）、或写库成为瓶颈时，缓存收益会指数级放大。当前场景测出 1.3 倍是符合物理规律的真实值。

## 三、逐步加压找拐点（`/dish/list` 缓存命中）

| 并发连接 | QPS | 平均延迟 | P99 | 错误 |
|---:|---:|---:|---:|---|
| 10 | 148.0 | 69.5ms | 222ms | 0 |
| 25 | 155.3 | 153.4ms | 228ms | 0 |
| 50 | 166.0 | 298.3ms | 460ms | 0 |
| 100 | 172.4 | 551.1ms | **1170ms** | 0 |
| 200 | 183.9 | 540.0ms | 1190ms | **167 次读超时**（约 5.7%） |

**拐点结论：**

- 并发从 10 涨到 200（20 倍），QPS 只从 148 爬到 184（**1.24 倍**），系统在 25~50 并发即接近吞吐上限；
- 但 P99 从 228ms 急剧恶化到 1.17s（100 并发）；**25~50 并发是甜点区**，再高是拿秒级延迟换几个 QPS；
- 200 并发出现 **167 个读超时**，但**没有任何 Non-2xx（无 5xx/拒绝）**——服务没崩，是"软过载"：请求在队列里排队，慢的等到超时。

**瓶颈定位（归因已修正）：主因是 CPU，不是数据库连接池。** 最初怀疑 HikariCP `maximum-pool-size=10`，但被两条对照证据推翻：

- `/ping` 不获取任何连接、不验 token，只返回字符串，也只有 406 QPS——连接池大小与它无关，连接池解释不了；
- vmstat 显示 CPU 打满（us+sy≈100%）且运行队列 r 长期 20~50——若瓶颈是等数据库连接，线程应阻塞在连接获取上、CPU 会有空闲，而不是 CPU 100% 且大量线程排队等 CPU 时间片。

> 注：早期版本曾写"缓存命中路径不执行 SQL、不获取连接"，实际代码里 `DishServiceImpl.list()` 第一行就调 `getCurrentFamilyId()` → `selectById(userId)` 查了一次 user 表，借了一个连接。这条证据不成立，已删除；真正排除连接池的是上面两条。

真实机制：2 核上每请求的固定开销（JWT HMAC 验签 + Redis 黑名单读 + 50 行 JSON 反序列化/序列化）被放大，Tomcat 100 个线程在两个核上时间片轮转，处理能力在约 150~184 QPS 到顶，多出的并发进入 `accept-count` 队列排队，直到超时（零 5xx 的软过载）。HikariCP=10 最多在高并发查库场景叠加次级影响，不是全局拐点。

> **已实锤（vmstat 秒级监控，100 并发压 `/ping` 时采样）**：压测期间 `us`+`sy`≈100%（us 73~81% / sy 19~27%）、`id`≈0、`wa`=0、`st`=0——
> - `st` 全 0：排除云主机被宿主机抢核（轻量服务器无 CPU 积分机制，也未降频）；
> - `wa` 全 0：排除磁盘 IO 等待；
> - 运行队列 `r` 长期 20~50（2 核机器，正常应 ≤2），大量线程在排队等 CPU，这是延迟飙升与超时的直接原因；
> - 上下文切换 `cs` 高达 0.7~1 万/秒、内核态 `sy` 占 1/4：**Tomcat `threads.max=100` 对 2 核机器配置过大，100 个线程在 2 个核上空转抢占，调度本身白白烧掉约 20%~25% CPU**。
>
> 保留项：wrk 与服务同机，CPU 打满中含压测客户端自身开销，服务真实容量需用另一台机器压测确认，但瓶颈类型（CPU）不受影响。实例为 Intel Xeon Platinum 2 核、可用内存约 1.6G（压测时 available 约 420M，非瓶颈）。

### 线程数对照实验（threads.max 100 vs 8，均 100 并发压 `/ping`）

| 配置 | QPS | 平均延迟 | 最大延迟 | 超时数 | 运行队列 r | cs/秒 | 内核态 sy |
|---|---:|---:|---:|---:|---:|---:|---:|
| **threads=100（默认）** | 729 | 138.8ms | 1.99s | 16 | 20~54 | 0.7~1.0 万 | 19~27% |
| **threads=8** | 453 | **17.6ms** | **168ms** | 114 | 6~12 | 0.5~0.8 万 | 13~22% |

**反直觉但正确的解读——线程数是「单次延迟 ↔ 并行度」的权衡，不是性能旋钮：**

- 降到 8 后，被处理请求的平均延迟从 138ms 暴降到 **17.6ms（-87%）**、最大延迟从 1.99s 降到 168ms，`sy` 与 `cs` 明显下降——**证实"线程过多导致上下文切换浪费"成立**，处理中的请求能拿到充足 CPU、快速完成；
- 但 QPS 反而从 729 降到 453（-38%）、超时从 16 增到 114：8 个线程**同时只处理 8 个请求**，100 并发里其余 92 个在队列中，114 个排到超时。
- 用 Little's Law 验证（并发数 N ≈ QPS × 延迟）：`8 / 0.0176 ≈ 454`、`100 / 0.138 ≈ 724`，与两次实测 QPS 几乎完全吻合。
- 结论：**线程贴近核数时单次延迟最优、切换浪费最小，但并行度被线程数封顶；线程远多于核数时用切换开销换来高吞吐，却让所有请求都变慢、长尾恶化。** 真正的天花板仍是 2 核 CPU 总量，调线程只改变"怎么分配这有限的 CPU"。
- 生产做法：① 线程数取核数的 2~4 倍（2 核轻 IO 服务约 **16**，8 过紧、100 过松，最终值按业务接口实测）；② **必须在前面加限流/过载保护**，让超过容量的请求快速失败（429），而不是像 8 线程这样在队列里干等到 2s 超时；③ 要更高总并发，靠降每请求开销或升配，不靠堆线程。

## 四、压测前发现并修复的真实部署事故（重要）

压测前的链路自检发现：`/ping` 始终正常，但**所有查库接口（登录、菜品、备忘）一律 500**。日志堆栈最底层：

```
java.sql.SQLException: Access denied for user 'root'@'localhost' (using password: YES)
```

排查发现 systemd 的环境变量文件 `/root/couple-nest.env` **只配了 OSS/JWT/WECHAT_MOCK，漏配了整组 `MYSQL_*` 变量**。Redis 因有默认值能连，MySQL 密码无默认值导致 HikariCP 拿不到连接。

**根因启示：** 只检查进程存活的健康检查（liveness）会给出"服务正常"的假象——`/ping` 不碰数据库，进程和 Web 端口都在，但核心链路已断。生产应增加**就绪探针（readiness）**，真正校验数据库/Redis 连通性后才放流量。

## 五、后续优化方向（按性价比排序）

1. **Tomcat 工作线程数调小并做对照实验（已定位、待验证收益）**：vmstat 显示 `cs` 上万、`sy` 占 1/4，把 `server.tomcat.threads.max` 从 100 降到 8（2 核的 2~4 倍），重压 `/ping` 对比 `cs`/`sy`/QPS/P99，预期切换大降、把调度浪费的 CPU 还给业务，P99 更稳。线程数对 CPU 密集/轻 IO 服务应接近核数，而非默认 100；
2. **健康检查升级为 readiness 探针**：探活时 SELECT 1 + Redis PING，避免本次事故复发；
3. **降低每请求固定开销**（针对 CPU 主因）：JWT 黑名单加 Caffeine 本地短缓存（登出主动失效）、精简/异步访问日志、大列表分页或字段裁剪减少序列化；
4. **过载保护**：限流初始阈值约 **100 QPS**（饱和点的 60%，上线后按监控校准），超限快速失败返回 429，而不是排队到 200 并发时让 5.7% 的请求超时；
5. **压测方法论修正**：先 warmup 再计时、固定场景顺序；用另一台机器压测，避免工具与服务同机抢核（本次 vmstat 已证明同机压时 CPU 100% 被压测端+服务端共同占满）；
6. **带宽（公网真实硬墙，本机 loopback 未测到）**：5Mbps 峰值 ÷ 约 7.2KB 响应体 ≈ 87 QPS，比 CPU 上限更早封顶，需结合实例带宽配额评估；
7. **规格与连接池**：CPU 实锤打满且无 steal，2 核容量即此为止，要更高吞吐优先升配（独享型）；HikariCP 仅在实锤查库排队时再调，不盲调。

## 六、结论摘要

> 独立完成情侣小窝服务端的**单机部署与压测**：用 wrk 在 2C2G 服务器上对只读接口做基准测试和并发加压。基于 Cache-Aside + Redis 实测，列表接口 QPS 从 87 提升到 113（约 1.3 倍），并通过对照分析确认该数据量下系统耗时主要在 JWT 鉴权与 50 行 JSON 序列化等固定开销、而非数据读取，缓存的价值在于给数据库留出余量；10→200 并发梯度压测中 QPS 走平（148→184）而 P99 从 69ms 升到 1.19s、200 并发出现 167 次超时但零 5xx，我用零业务逻辑的 `/ping`（仅 406 QPS）和不查库的缓存命中接口同样超时这两个对照，排除了数据库连接池，把瓶颈定位到 CPU 固定开销，并给出限流（阈值约 100 QPS）、降低每请求开销、readiness 探针、容量升配等方案；同时主动说明压测工具与服务同机抢核、首场景未预热两个已知瑕疵。压测前的链路自检还发现环境变量缺失导致数据源不可用的部署事故，推动健康检查从存活探针升级为就绪探针。

## 七、复现方式

```bash
# 数据准备（服务器）
mysql -uroot -p couple_nest < /root/seed.sql
# 执行压测（约 3 分钟，自动登录拿 token）
bash /root/run-bench.sh 2>&1 | tee /root/bench-result.txt
# 清理
mysql -uroot -p couple_nest < /root/cleanup.sql
```

脚本与数据：`deploy/bench/`（run-bench.sh、seed.sql、cleanup.sql、check.sql）。
